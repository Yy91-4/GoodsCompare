# GoodsCompare 头脑风暴对话记录

**日期**: 2026-06-03

---

## 对话摘要

### 用户初始需求
做一个可以在手机端运行的，能在各个外卖平台上实时比较相同商品价格的 App/小程序，覆盖淘宝闪购、美团、京东。

### Q1: 产品形态选择
- A) 微信小程序
- B) Web App (PWA)
- C) 独立 App (React Native / Flutter)

**选择: B — PWA**

理由：跨平台、可添加到手机桌面、无审核限制、开发自由度最高。

### Q2: 数据获取策略
- A) 自动抓取 — 用户体验最好，但有法律和技术风险
- B) 用户粘贴链接 — 稍麻烦但可控
- C) 用户手动录入 — 最简单但体验差
- D) 混合模式 — 优先自动，失败降级手动

**选择: D — 混合模式**

### 补充讨论: 法律风险
讨论了数据抓取的法律灰色地带：
- 违反《反不正当竞争法》第12条（大规模抓取）
- 违反《网络安全法》第27条（未经授权访问他人系统）
- 平台数据权益受法律保护（淘宝诉生意参谋案、美团诉二维火案）
- 个人小规模低频使用风险相对可控
- 策略：仅做单页面公开信息低频查询，不加反爬对抗，见风控即降级

### Q3: MVP 功能范围
- A) 纯价格对比
- B) 对比 + 收藏/历史记录
- C) 对比 + 收藏 + 跳转下单
- D) 对比 + 收藏 + 跳转下单 + 价格走势

**选择: A+B+C+D — 全功能覆盖**

### Q4: 用户规模
- A) 个人自用
- B) 少量共享用户
- C) 公开产品

**选择: A — 个人自用**

简化点：无需用户系统、无需多租户数据隔离、部署在自己机器即可。

### Q5: 后端技术栈
- A) Python (Flask/FastAPI)
- B) Node.js (Express/Hono)
- C) 纯前端 + 第三方服务

**选择: A — Python FastAPI**

理由：已有 Python 经验、爬虫生态丰富、部署简单。

### Q6: 前端方案
- 方案一: FastAPI 全栈 (SSR + Jinja2)
- 方案二: FastAPI 后端 + 轻量前端 (Vanilla JS/HTMX) ⭐ 推荐
- 方案三: FastAPI 后端 + React 前端

**选择: 方案二**

推荐理由：前端轻量无需 Node 工具链、PWA 支持完整、移动端体验好、维护负担小。

## 最终确定的设计

| 维度 | 决定 |
|------|------|
| 形态 | PWA |
| 前端 | Vanilla JS + HTMX，无 Node 工具链 |
| 后端 | Python FastAPI |
| 数据库 | SQLite |
| 数据获取 | 混合模式：自动抓取优先，失败降级 |
| 功能 | 搜索对比 + 收藏 + 跳转下单 + 价格走势 |
| 用户 | 个人自用，无需登录 |
| 部署 | 个人本地机器 |

## 架构概要

```
PWA 前端 (Vanilla JS + Service Worker)
    │ HTTP/JSON
FastAPI 后端
    ├── API 路由: 搜索、收藏、历史、价格趋势
    ├── 服务层: 搜索聚合、收藏管理、价格追踪
    └── 抓取层: 各平台适配器 (淘宝/美团/京东)
            │
    SQLite: products, price_records, history
```
